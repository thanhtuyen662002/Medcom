# Phase 1 adversarial risk register

2026-10-01 supplemental owner-guide review adds 40 security/data and 52 user/operations tabletop cases in `docs/reviews/PHASE2_SECURITY_DATA_ATTACK_REVIEW.md` and `docs/reviews/PHASE2_USER_OPERATIONS_ATTACK_REVIEW.md`. Those registers reuse canonical issue owners and acceptance controls rather than creating a parallel implementation backlog. Source/runtime evidence and Phase 1 closure remain open.

Status: ACTIVE. This register defines failure classes, required mitigations, detection signals and acceptance tests. Source-specific behavior that is not proven remains UNKNOWN rather than being assumed.

## Gate rule

A risk class is not closed because a design sentence exists. Closure requires a bound surface/contract plus an executable or reviewable acceptance test. During Phase 1, tests may be specified rather than executed where the Web implementation does not yet exist. C#-dependent facts remain explicit UNKNOWNs for the next verification round.

## Evidence-bound priority attacks

1. **Persisted DAT filters**: ERP evidence proves configurable FieldID/operator/data type/order/visibility. Therefore RISK-SEC-001 and RISK-CONFIG-001 are immediate migration gates: browser metadata cannot become SQL or authorization.
2. **SY_* configuration tables**: DB evidence proves a legacy configuration engine exists, but enforcement/precedence is not proven. Effective-config diagnostics and facade validation are required before reuse.
3. **RPX embedded scripts/subreports/barcodes**: report parity must test semantics, dependency sets and machine-readable output, not screenshots only.
4. **No verified event/version source**: no current surface may claim correctness-preserving realtime PUSH. SWR/POLL/SNAPSHOT remains the safe product contract until RISK-RT-001 prerequisites are evidenced.
5. **Mixed-client coexistence**: Phase 1 assumes Windows and Web overlap during migration, making RISK-ROLL-001 and RISK-DB-001 release gates rather than optional hardening.

## UNKNOWNs reserved for source verification

Exact permission enforcement path; company/branch/storehouse authority precedence; legacy transaction/locking order; row-version or equivalent tokens; idempotency behavior; trigger/procedure side effects by workflow; config override precedence; alias A/B filter bindings; runtime report reachability/print defaults; authoritative event source; background integration inventory; file/template storage and retention. These are not waived risks and must be bound when evidence appears.
